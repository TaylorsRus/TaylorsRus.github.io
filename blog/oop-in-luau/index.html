OOP in Luau

I thought it was important to get some of my thoughts out regarding OOP, specifically in Luau / Roblox. It’s been really important in my recent code.

I’d like to preface this by saying there is no correct way to do OOP. In this post, I’m going to be providing rationale towards my personal do’s and dont’s, but it’s all subjective, even if I sound really really objective in my sentence framing, really, it’s just an opinion.

I’d also like to highlight that a lot of my opinions will come from the perspective of a Roblox developer, that comes with the baggage of Roblox idioms that can have an impact on how I think.

Let’s start by just creating a dummy class, which attempts to highlight every core facet of how I tackle OOP.

type Object = {
	_privateProperty: any,
	PublicProperty: any,
	PublicMethod: () -> (),
}

local ClassProperty = nil

function privateMethod(self: Object)
end

function PublicMethod(self: Object)
end

function ClassFunction()
end

function new(): Object
	return {
		_privateProperty = nil
		PublicProperty = nil
		PublicMethod = PublicMethod
	}
end

return {
	new = new
	PublicMethod = PublicMethod
	ClassFunction = ClassFunction
	ClassProperty = ClassProperty
}

Bare in mind that some of these practices aren’t exclusive to OOP, but are just how I handle modules in general. that being said, OOP has had an impact on how I handle modules period.

Let’s go through some concepts that we see in this example, so we can create an overview of how we got here.

The model Link to heading

There are two main models of OOP in my opinion, and within them, a few different sub paths that can be taken to slightly alter the workflow. I’m going to refer to the one I used as the direct model. I’d love to learn a colloquial term for this in the future. As a community, we should really attach some solid terminology to this, because things can get lost in jargon pretty quickly.

The other model, is the metatable model, where you leverage the __index metamethod on the Class table itself; such that when you call object:Method(); Although it will not technically exist, it will trigger a redirect onto the class, and pass the object along, where the method will exist. I’m not a fan of this model, you have to trick the type solver to say “The object has this method”, when eally, the object just holds the state. Below is an example.

local Class = {}
Class.__index = Class

function Class.new()
    return setmetatable({}, Class)
end

function Class.Method(self)

end

What’s potentially neat about this model, is it allows inheritance, which is something the direct model doesn’t allow. Due to how you are directly linking an object to it’s methods, you’re creating a tight bond which stops at it’s station, but it can’t go any further. With metatables, you can chain them together to create a form of inheritance, which can be especially useful if you’re using OOP as a foundational paradigm in your codebase. I don’t do this though, I use it complimentarily to manage state that I want to drag around with me, so it’s not worth the extra complication and tricky-ness with the types.

Casing Link to heading

This is a hot topic, so much so that some will forego casing standards, and just choose one simple case for everything, and I see the merit, but I still believe that the benefit of being idiomatic as well as having some clarity in your code, out weighs the simplicity of one case for everything, hence why we have:

  • PascalCase for anything public, this isn’t a class exclusive rule, if it leaves the module it’s in at some point, this applies
  • camelCase for anything private, so private methods in this example, with an extra underscore as a symbol of extra clarity in an object, since we can’t have real private properties in Luau, we make do by making it crystal clear to the user of an object what is private, these fields benefit from needing less thought behind them during the API design phase; What’s public matters, What’s private, meh.

The exception Link to heading

new is the exception here, it’s a common idiom within Roblox for constructors to use camelCase.

Explicit constructors Link to heading

I believe in continuing the roblox tradition of defining an explicit new constructor, used like local object = Class.new().

I do this because of the un-mistakeable clarity it provides, aswell as the scalability. They’re both minor, but they are a contributing factor. If we did local object = Class(), we would forever be limited to one constructor, which might in the future, guide poor API, with new args in the constructor, instead of a new constructor. It can also be a little confusing, as elsewhere in your codebase, you may use modules that return functions, which can blend in with your classes, especially when these modules also happen to return a small stucture to manage their state. This however I think is a problem in-of itself, in our hypothetical, you’re using a form of OOP, but not following a convention, which allows it to become muddled within your codebase alongside your conventional OOP.

Publicized methods Link to heading

By giving access to all of our methods via the class, sort of like class functions. We enable the detachment of our state from the object. While this technically enables being able to use a method with structure which wasn’t constructed via the class, this is not useful, and instead, the most useful byproduct of this is networkability.

If we store our class in ReplicatedStorage, we can utilize something like this:

local ReplicatedStorage = game:GetService("ReplicatedStorage")

local Class = require(ReplicatedStorage.Shared.Class)

local object = Class.new()
local player = ...

ReplicatedStorage.Events.ReplicateObject:FireClient(player, object)

local ReplicatedStorage = game:GetService("ReplicatedStorage")

local Class = require(ReplicatedStorage.Shared.Class)

ReplicatedStorage.Events.ReplicateObject.OnClientEvent:Connect(function(object)
    Class.Method(object)
end)

Now, this does come with it’s own sacrifices. You cannot utilize the colon sugar syntax, and your forced to leave your source code open to decompilation by leaving it exposed to the client, but it is something to consider. Personally, I prefer to break down the state of my class, and only replicate what I need to.

If you’re not a fan of tracking the type of your methods when using the direct model, you can also use this to have implicit method typing from the class table.

Use case Link to heading

I’m using OOP alot now-adays. It’s my go to whenever applicable. Sometimes, it’s super stereotypical, but othertimes, maybe not. I use it as abstraction layers ontop of other objects, which has led me to discover really cool patterns like this!

type BaseStructure<T> = {
    Field: any
    Method: (T) -> ()
}

type ExtendedStructure = BaseStructure<ExtendedStructure> & {
    NewField: any
}

Be careful with recursive generics however, if you have a structure like this;

type Object = {
    ExtendedStructure: ExtendedStructure
}

type BaseStructure<T> = {
    Object: Object
    Method: (T) -> ()
}

type ExtendedStructure = BaseStructure<ExtendedStructure> & {
    NewField1: any
}

You’ll find yourself with a type error, due to the cyclical nature of the type, where you need to abstract the point of recursion

type Object = {
    ExtendedStructure: ExtendedStructure
}

type ObjectField = {
    Object: Object
}

type BaseStructure<T> = {
    Method: (T) -> ()
}

type ExtendedStructure = BaseStructure<ExtendedStructure> & ObjectField & {
    NewField1: any
}

I’ve also played with the syntax when appropriate, such as an abstraction I’m currently planning which will use Query as the constructor, but still return an object and will largely stick to convention apart from that.

The takeaway Link to heading

Standards are important in my opinion. Defining one can set you up for less headaches in the future, it may seem like a large upfront cost in terms of the time you spend setting the standard, but it allows the freedom of really not thinking as much, and just sticking to the standard, that’s to say it doesn’t just give you the benefit of your code being better when going back, but also just being easier to write as you’re going forward. I’m really happy with the standard I’ve defined for myself with objects, and I wanted to share it because I think it can be of benefit to individuals who get overwhelmed with the amount of options. My goal with this perosnal structure was to strip out as much fluff as possible, even though we have still left a bit of fluff in there, otherwise it’d be completely snake_case!
