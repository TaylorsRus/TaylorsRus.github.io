Principles & Arbitrariness

Coding principles can be super daunting, in conjunction with extremely guiding and rewarding to follow. For me personally, it’s caused a lot of paralysis-via-analysis while I’m coding, and so I thought I would go over some of the principles which keep coming back to both haunt me, and guide me; my personal experiences with them, and how I’ve overcome some philosophical difficulties in relation to them

DRY (Do-Not Repeat Yourself) Link to heading

This could be considered the cornerstone, or maybe just the most well known and established principle, Do-Not Repeat Yourself.

At a fundamental level, it’s pretty easy to follow. Write re-usable functions, combine code which does the same thing under args and config, centralize your data so code in multiple locations can refer to one data point, so on and so forth, but once you have a solid understanding on the basics of DRY, the level of scrutiny you can give to your code really sky rockets, which can cause a crippling sense of “could this be done more principally?”.

I’ll give a real world example. Recently, I was modifying the API of a basic wrapper around a datatype, take in an initial value, and use setters/getters so you can listen in with an injected changed event. I wanted to create two upgrades to this API

  1. I wanted read only values, a valid and simple addition
  2. I wanted to be able to bind a value object to a property, acting as the new point of contact for that property on the object

It spiralled pretty quickly, a lot of over-engineering, and eventually I created a secondary wrapper, PropertyValue; placed it in the same directory, and now I had what I believed was a clear separation of concerns.

But was this a shining example of proper DRY?

The short answer? No. Internally in the API, as well as the file name, and the existence of it next to it’s wrapped counterpart, Value, was in distinct violation of DRY. To strictly follow this principle, I would need something like having Value/Property be the wrapper, accessed with something like Value.PropertyBinder.new(), or Value.newPropertyBinder. With the former violating dry in a different way.

Here’s the point, and this is something I had to learn through brutal stagnation. DRY is important, but the less influential your repetition is, the harder it will be to reason what is the better alternative. In this case, I have 3 wrappers for Value, in the same directory, and that works really well with Luau LSP’s auto import, and doesn’t clog my directory, because said directory is not already a mess. I’m playing into other principles at the behest of DRY, because they usually impact the ongoing coding experience more often.

DRY violation is pretty linear, the more you repeat yourself, the less maintainable your code gets, but below a baseline, other things take precedence. It is useful to a point, and then it is a burden.

YAGNI (You Aren’t Gonna Need It) Link to heading

I’ll gloss over this one, I think it’s pretty straight forward and self-explanatory, in a way which needs less context then other principles.

The second you do think an abstraction of some kind would provide value; Go for it, but until it isn’t, don’t spend too long bargaining about it’s use.

The example I’ll give is cross platform support. Unless you’re experienced developing for multiple platforms, have spent time creating some sort of API for handling it, or are simply interested in doing exactly that, it’s something I stay away from.

The reason for me is simple. My game doesn’t need mobile support if it never releases, building mobile support does not get towards the goal of releasing it, and while I do tend to go off on side quests that aren’t directly related to features, they never get so far away, to the point I’m creating a thing that might never even be used.

Now, a common counter-arguement for this perspective is that you’ll have to undo your work, and my response would be, you’re going to do that anyways. If you care about your work, and aren’t pushing code to production ASAP, the chances you revisit things often over and over are high. The entire setup you have for bringing user input all the way to it’s correlated functionality could be scrapped, including the mobile support you pushed to include! Beyond that, trying to juggle mobile support can be an ongoing trifle in creating features, which can be disuading, or even debilitating. With all that being said, Roblox has recently released the InputActionService to tackle problems like this, trying to make it trouble free.

KISS (Keep It Simple Stupid) Link to heading

This seems really easy to follow at first, all you have to do is not overthink things, get to the point, and don’t go above-and-beyond the project criteria. The uncomfortable truth is that as you’re developing something, you often don’t have the clarity to do this, because it often requires taking a step back, while your primary objective is stepping forward.

I’ll come back to my Value example. Before PropertyValue, the api looked like this!

local propertyValue = Value.fromProperty(instance, initial, propertyName)
local propertyValueFactory = Value.newPropertyFactory(instance)
local propertyValueFromFactory = propertyValueFactory:new(intial, propertyName)

Now on the surface, this isn’t too bad, but consider this. Before this, it was an overloaded constructor on new, and even in the above state, it had to inject itself into the functionality of a value, to bypass things like it’s setter method, which ordinarily wouldn’t persist onto the property it’s watching, and you see where it goes.

Because my goal was “upgrade Value to support property”, all I could see was a solution that was intertwined with it, but after taking a step back, I was able to identify that this is not an “upgrade” to value, but a layer, an extension, because this is completely new functionality, and only uses Value as a base for it’s Getter, base Setter functionality, and changed event.

So in short, for me, KISS has been about being able to take a step back, after the first prototype or two of a new design.

SoC Link to heading

This is maybe my favourite principle at the moment, it provides me with such jaw dropping, OMG moments, and has given me a new favourite word- abstraction.

It leans back onto KISS, sometimes, as your idea develops or changes, and your scope widens, this is no longer the job of just one API, it would be neater handled by separate sections doing their own things.

Let’s use this example, I’m making a fighting game, and I’m creating the code which runs when your attack lands on someone. This is the section of the code which deals with the last hit in a combo, the one which applies a knockback, and a ragdoll.

Initially, one might write all this code in one, perhaps separating the concerns into smaller functions, maybe not separated enough, but a good demonstration of the fundamental idea.

To me, a ragdoll and a knockback are prime real estate for their own files, which take in a structure or instance (usually and probably, a character), and apply those effects. Ragdoll.Build/Enable/Disable/Toggle for example. Here are some more fuctionalities, in the same genre of code, which might benefit from completely separated concerns:

  • Visual effects (particles, beams, 3d parts)
  • Animation loading / property application
  • Sound playing / property application
  • Skill casting

Here’s the rule I stick to; If behaviour starts to get advanced around a concept, abstract it. Circle back to the name of your function, and ask, “is this tightly related to this concept, or can it exist independently?”

While an attack can cause an explosion, require an animation or a sound effect, and may cause someone to ragdoll, all of these things can occur in absence of an attack, and so they’re prime real estate to be be handled separately. What’s important is you judge the scale of your behaviour, Things like skills, and ragdolls are obvious examples, but with something like a sound, if all you’re doing is parenting a sound, playing and then destroying it, perhaps you do not need an abstraction, but if you’re always parenting it to the same place, cleaning it up on destruction, applying modifiers, and fading in/out, perhaps you need an API which will help you manage these duties, at which point, to play nicely with SoC, you should abstract it.
